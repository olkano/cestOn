Research and comments

The full assessment distinguishes local findings, documented provider capabilities and features that still need development.

1. The main change is the product model

Your objection is valid. A project/session browser should be the primary experience. Keep tasks, permissions, verification and update records behind the scenes for work cestOn actually starts. Fixtures stay in development. This is more than a homepage reskin, because current command and execution flows are task-bound.

2. Both providers can associate history with folders

Codex supports directory and source filters in thread/list. Claude exposes session-listing and history APIs; the installed SDK includes directory/worktree and programmatic-session options. A global IDE history list does not mean folder metadata is absent.

The current fallback only matches exact registered directories and limits discovery to each project's selected provider. It needs better provider-neutral indexing, subfolder/worktree resolution and an explicit unresolved-path state.

3. Related sessions should be suggestions, not merged conversations

Use parent/fork links, repository/worktree context, titles and shared references first. Show why two sessions look related and let you keep or reject the link. Same repository alone is weak evidence. Deeper conversation analysis should be opt-in; its accuracy and cost still need evaluation.

4. Live control needs a real integration

Codex offers resume, steer and interruption on its app-server connection. That does not automatically connect a new process to an IDE-owned live session. Claude documents Remote Control from existing CLI and VS Code sessions in its own web/mobile clients, subject to account eligibility. A tested cestOn control bridge remains separate development work.

Start with visibility and returning to the provider's original UI. Offer managed continuation as an explicit alternative, preserving the original session.

5. cestDone already has isolation mechanisms, but the clutter's cause is unconfirmed

Its inspected backend supports CESTDONE_CODEX_HOME and requests a cestdone tag for new threads. The inspected settings and saved daemon dump did not show a home override; the live service environment and known job/session matches were not verified. A bounded interactive-history sample contained no cestDone tag, so a shared-home cause is not established.

Verify actual IDE exclusion and resume behavior. Do not delete old history or make every job ephemeral. OpenAI's independent batch-job guidance.

6. Google Drive document folders belong in the same view

Git is optional. A locally available document folder can be a project. Add it by folder picker or natural language with a path confirmation. Preserve ambiguous or offline paths instead of silently losing their sessions. Keep cestOn's database and provider state outside synchronized project folders.

7. A useful first revision can be read-only
  1. Connect approved history sources and show existing folders with both providers.
  2. Display session titles, checkout context, origin, activity and control availability.
  3. Add automation filtering and explained related-session suggestions.
  4. Then certify provider-specific live-control integrations.

No mandatory task creation for visibility. No promise of control over every existing session. Review the tradeoffs and acceptance checks before authorizing a redesign.

Recommended decision

Adopt the project/folder → sessions model. Keep the durable backend, make discovery useful before live control, and treat scheduler-history isolation as a separately verified operational change. The application and active specifications have not been redesigned by this preview.
