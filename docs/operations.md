# Local operation and recovery

Use Node 24 and a verified local bundle on Windows under the intended user account. Configuration, SQLite, credentials, journals and releases belong in a dedicated owner-only data folder outside Git and synchronized folders. The supervisor, coordinator and broker run as separate processes. Native workers receive isolated project snapshots; their changes are delivered as review artifacts. They cannot write back to an unowned source project.

Create a bundle with `npm run package:local`. It runs verification, security and update suites and writes an immutable directory, ZIP and SHA-256 under ignored `artifacts/`. Inspect its manifest and dependency notices. The application remains unlicensed for redistribution until the owner selects a license.

From the unpacked directory, run `node dist/apps/supervisor/src/cli.js init --bundle . --config CONFIG --root DATA`. Initialization requires an empty destination, restricts access to the current user, copies a stable supervisor outside versioned releases, and leaves the installation stopped. Use a configuration derived from the contract in the operations specification. Provider profiles remain blocked until their live certifications pass.

Run the same CLI with `start`, `status`, `version`, `doctor`, `pair`, `backup`, or `recover`, always supplying `--root DATA`. Pairing invitations appear only in a private interactive terminal and expire in ten minutes. Other commands emit structured JSON. Start does not register persistence. `stop --scope coordinator` preserves running broker work; `stop --scope all` requests interruption and reports unresolved work. No command kills an unrelated process to free a port.

`install-startup --plan` and `uninstall-startup --plan` prepare the exact current-user task identity without registration. Omitting `--plan` is an explicit persistence operation. The installer refuses to overwrite or remove a task whose identity, action, owner or installation description differs. Sleep and sign-out can interrupt availability. Physical sign-in, reboot and locked-session acceptance remain separate checks.

Backups use SQLite's consistent snapshot API and authenticated encryption with a key wrapped by current-user Windows DPAPI. Copying a live SQLite file is not a backup procedure. Update-worker journals, update authority and candidate metadata are included with reconciliation material. A restored backup stays paused until accepted commands and broker receipts after its cursor have been reconciled; the ordinary resume command cannot bypass that gate. Keep the previous installation and its journals until recovery is verified. Cross-user backup portability is not supported by DPAPI.

Use `recover --backup NAME --target EMPTY_DATA` to restore, even if the original database no longer opens; backup decryption reads the bounded archive header and uses owner DPAPI independently of that database. then `recover --root EMPTY_DATA --reconcile-from STOPPED_SOURCE` to compare all durable state and reconciliation material under exclusive OS locks. An unchanged, resolved source can be retired after its immutable current/previous releases and stable supervisor bootstrap have been copied and hash-verified in the replacement. The replacement remains paused for deliberate resumption. Unknown update-worker receipts also prevent retirement. Any newer state or unresolved work keeps recovery blocked; preserve both roots and create a fresh verified source snapshot. If the intact source is unavailable, its missing acknowledgements cannot be proved absent. The retired source cannot start another coordinator or broker.

The supervisor verifies all release bytes, rebuilds candidates under the constrained verification host, checks protected paths independently, and journals activation before switching an atomic pointer. Routine rollback uses the current database. A failed candidate returns to the previous verified release; failed rollback leaves recovery frozen. Destructive or unproved schema changes cannot activate automatically. The private CLI remains available when the web coordinator is unavailable. Frozen supervisor recovery exposes a separate read-only loopback page, whose URL appears in private status. It lists release integrity and backup verification without task content or write endpoints. After diagnosis, the explicit `recover` command can retry the retained verified release; startup never loops through a failed rollback automatically.

Logs contain allowlisted fields and rotate at 10 MiB with five generations. Startup and daily cleanup retain uncertain receipts, active work and backups. Release cleanup keeps the configured verified generations plus current, rollback and pending releases; corrupt/unknown or credential-bearing directories are preserved for diagnosis. Acknowledged terminal broker events older than 30 days can be pruned without resetting event sequence identity. Receipt compaction preserves one durable record per command; storage exhaustion fails closed rather than forgetting deduplication history. No cleanup edits provider-owned history. Doctor checks a free or authenticated owned listener, database schema, broker protocol, profile certification and zero-model authentication probes. Clock plausibility is checked locally; trusted clock-skew verification remains explicitly degraded without a configured time source.
